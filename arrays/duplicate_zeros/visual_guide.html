Duplicate Zeros

Every zero in a fixed-length array needs to become two zeros, and everything after it shifts right — without a second array, and without touching anything past the original end.

Input
→
Output
  • Fixed length. The array never grows — it stays exactly as long as it started.
  • Every 0 doubles. Each zero you encounter becomes two zeros, pushing later elements right.
  • Overflow is dropped. Anything that would land past the original length is simply never written.
  • In place. The array is mutated directly — nothing is returned.

The trap

Why "shift on every zero" is O(n²)

The obvious approach works: scan left to right, and the moment you see a zero, insert a second zero right after it and shift everything past that point one step to the right. It's correct — but each shift touches every element after the insertion point. Do that for every zero in an array of all zeros, and you're paying O(n) work, up to n times.

The optimal trick never shifts more than once. It figures out, ahead of time, exactly which elements survive the truncation — then writes the final array from the back, in a single backward pass.

The subtle part

Why walk backward, not forward?

Duplicating a zero always pushes data rightward. If you write forward while reading forward, the write pointer races ahead of the read pointer and starts overwriting cells you haven't read yet. Walking backward guarantees the opposite: the write pointer is always at or ahead of the read pointer, so you finish reading a cell before anything is ever written into it.

Beyond this problem

Main takeaways

Duplicate Zeros is a good vehicle for patterns that show up constantly in array problems — worth carrying past this one exercise.

  1. 01

    "In-place" is a hint to count first, act second.

    The naive approach (shift on every zero) is correct but redoes work — each shift is O(n), and you might do it O(n) times. The fix isn't a cleverer shift, it's splitting the problem into two separate passes: one that only figures out what the final array looks like (where does everything land, where does it get cut off), and one that writes it. Whenever you catch yourself repeating an O(n) operation inside a loop, that's the signal to ask "can I precompute this in one pass instead?"

  2. 02

    Two pointers isn't one specific trick — it's "read and write don't have to move together."

    Here read and write advance at different rates (a zero consumes 2 write-slots but only 1 read-slot), which is exactly why you need two independent indices instead of one loop variable indexing both sides.

  3. 03

    Direction of traversal matters when reads and writes overlap.

    This is the sharpest lesson in the problem. Because duplicating a zero always pushes values rightward, write is always at or ahead of read. Writing forward means you'd overwrite a cell before you've read its original value — silent data corruption. Writing backward guarantees every cell is read before it's ever written into. This exact idea — walk backward when the destination and source overlap and destination trails behind — reappears in merging two sorted arrays in place (LeetCode 88), string compression, and general in-place merge steps.

  4. 04

    Boundary/cutoff is an edge case worth naming, not just handling.

    The last zero you count might only get 1 of its 2 slots before the running total hits n. Giving that case a name (cutoff) instead of letting it fall out of an off-by-one is what makes pass 2 correct — it's a small example of "figure out the edge case explicitly before you write the loop that has to handle it."

  5. 05

    O(1) space means "a few scalars," not "no cleverness."

    The whole algorithm's state is read, write, a running total, and a boolean — that's the real meaning of O(1) auxiliary space, as opposed to allocating a second array of size n (which would trivially solve the problem but isn't the point of the exercise).

The two-pointer notes file already frames #1 and #3 well — those are the two ideas worth internalizing beyond this specific problem.

Before you write it

Common coding gotchas

The algorithm is the hard part — but "in place" turns out to be a surprisingly easy constraint to accidentally violate in every one of these languages, usually without an error telling you so.

Universal — applies no matter what you're writing this in

  • Reassigning the parameter doesn't mutate the caller's array.

    Setting arr = someNewArray inside your function only repoints your local variable — the array your caller is holding is untouched. "In place" means writing into existing slots (arr[i] = value) or using a method that replaces contents wholesale, never handing back a different object.

  • Building a same-length result and returning it isn't the same as solving it in place.

    It's a genuinely good way to work out the logic, and a good way to check your answer — but the submission has to end with the original array's cells changed, with nothing returned.

  • Forgetting the array is fixed-length.

    Every language below gives you a resizable list by default. The moment you append or insert a real element without immediately removing one to compensate, you've grown past n — and "elements beyond the original length are not written" is already broken.

Language-specific

  • Reaching for splice is the direct naive translation.

    arr.splice(i, 0, 0); arr.pop(); reads cleanly, but splice shifts every element after i — it's the same O(n)-per-call cost as the shift-on-every-zero approach, just spelled with a built-in.

  • Never iterate an array with for...in.

    It walks enumerable keys as strings — including anything inherited — not numeric indices in order. Use for, for...of, or .forEach instead.

  • Truthiness isn't the same as "equals zero."

    if (!arr[i]) happens to catch 0, but it also catches undefined and NaN — compare explicitly with arr[i] === 0 so the check means what you intend.

  • arr.length = n truncates in place.

    An easy-to-forget built-in: assigning to .length drops every element past n immediately, no loop or pop() needed.

  • number[] doesn't encode a fixed length.

    The type checker happily allows push, splice, anything that resizes — TypeScript gives you no extra protection against breaking the fixed-length rule here, despite the more precise-feeling types.

  • readonly number[] quietly rules out solving it at all.

    Marking input parameters readonly is good habit almost everywhere else in TS — but here it turns arr[i] = value and every mutating method into a compile error. The one parameter you actually need to mutate can't be readonly.

  • noUncheckedIndexedAccess changes what arr[i] is.

    With that flag on, indexing returns number | undefined instead of number. arr[i] === 0 still works fine, but passing arr[i] further downstream may force an unexpected narrow or assertion.

  • list.insert(i, 0) + list.pop() is the same naive trap.

    It reads even more naturally in Python than in JS, which makes it easier to reach for without noticing it's still an O(n) shift per zero.

  • Slice assignment mutates; plain reassignment doesn't.

    arr = new_values just rebinds the local name. arr[:] = new_values is the idiom that actually copies into the existing list object your caller is holding — the two look similar and behave completely differently.

  • is 0 is not the same check as == 0.

    CPython caches small integers, so arr[i] is 0 often happens to return the right answer — but is compares identity, not value, and Python 3.8+ will warn you about it for good reason.

  • The ! in a method name is the whole story.

    arr.insert(i, 0) mutates the receiver, but it's easy to assume the same of a non-bang method like arr.map { ... } — that returns a new array and leaves arr untouched. You'd need map! for it to count as in place.

  • Reassignment doesn't mutate here either — but Ruby gives you a clean fix.

    arr = result just rebinds the local variable, same pitfall as every language above. arr.replace(result) is the idiom that copies result's contents into the array object the caller already holds.

  • You can see this exact tension in this repo's own Ruby solution.

    The version in duplicate_zeros.rb that builds result and returns result[0...arr.length] reads cleanly and produces the right values — but it returns a new array rather than mutating arr, which is the "building a result and returning it" gotcha above, concretely.
