The trap

The tool you already know doesn't fit here

The hash-map approach from Two Sum still works — it's correct, and still O(n) time. But it needs O(n) space to hold the map, and this problem's constraints rule that out explicitly. This isn't a speed trap like the others in this series — it's a "the constraint changed under you" trap.

The optimal version uses the one thing the hash map throws away: order. Since the array is sorted, you always know which direction to move.

Ruby — reusing the Two Sum approach
def two_sum_ii_naive(numbers, target)
seen = {}
numbers.each_with_index do |value, i|
complement = target - value
if seen.key?(complement)
return [seen[complement] + 1, i + 1]
end
seen[value] = i
end
nil
end
