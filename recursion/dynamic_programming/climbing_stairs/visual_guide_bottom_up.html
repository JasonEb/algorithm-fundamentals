Climbing Stairs, Bottom-Up

The recurrence stays the same. What changes is the direction: instead of starting at n and waiting on smaller answers, start at the base cases and build up to n with a loop.

n = 5: fill the table left to right
ways[i] = ways[i - 1] + ways[i - 2]  for every i from 2 up to n
  • Same answers. Both directions compute the same values, 1, 1, 2, 3, 5, 8 and so on. Only the order differs.
  • No recursion. A loop replaces the call stack, so there is no depth limit to hit.
  • Only two values are ever read. That is what lets the table shrink to two variables.

Two directions

Same subproblems, opposite order

Top-down starts at the question, f(5), and keeps asking for smaller values until it reaches the base cases, then answers flow back up. Bottom-up skips the asking: it begins at the base cases and never needs to ask anything, because every value it needs is already in the table.

Top-down (recursion + memo)

ask down, answers return up

Starts at f(5). Each call waits until f(4) and f(3) come back. The call stack grows to about n frames.

Bottom-up (loop)

start at the base, build up

Starts at f(0). Each value is computed from the two before it. Nothing waits, and there is no stack.

About memory. Recursion is not a memory leak: every frame is released when its call returns. It does use stack space proportional to the depth, so the memoized version is O(n) space, and Ruby raises SystemStackError at roughly 10,000 to 12,000 nested calls (measured on Ruby 3.3). For n up to 45 that limit is never close. The bottom-up version has no such limit at all.

The conversion

Five steps from recursion to a loop

1
Find the dependency direction.

f(n) needs f(n-1) and f(n-2). Both are smaller values of n, so nothing depends on a larger n.

2
Compute in that order.

Since answers only depend on smaller ones, go from the base cases up to n. The recursion went the other way and waited.

3
Store results by state.

An array indexed by n replaces the memo hash. Slot i holds the number of ways to reach step i.

4
Handle the base cases by hand.

The loop cannot look at index -1, so ways[0] and ways[1] are set directly and the loop starts at 2.

5
Shrink the storage.

Each step reads only the previous two slots. Keep those two in variables and drop the array.

The update-order trap

Why the shift has to use a temporary

When you replace the table with prev and curr, the order of the assignments matters. Writing prev = curr and then curr = prev + curr reads a prev that was just overwritten, so curr gets added to itself. The results double at every step.

Why the tests can miss it. The wrong order gives the right answer for n = 2 (1 + 1 = 2), so a driver that only checks n = 1 and 2 passes. It first fails at n = 3. Keep n = 3, 4, and 5 in your checks.

Before you trust it

A short checklist

  • n = 1. The array version needs a slot at index 1, and the loop (2..n) should run zero times. The two-variable version needs an early return.
  • n = 2 and n = 3. These are the first values that use the loop, and 3 is where the wrong update order first fails.
  • Compare with the recursion. Keep the naive version as climb_stairs_naive and check that both agree for n = 1 to 20.
  • n = 45. The answer is 1,836,311,903 and it should return instantly.

Recap

Complexity

Bottom-up table

O(n) time · O(n) space

One pass, one array of n + 1 slots.

Two variables

O(n) time · O(1) space

The same pass, keeping only the last two values.

The same move works elsewhere. House Robber has best[i] = max(best[i - 1], best[i - 2] + nums[i]). It also reads only the previous two entries, so it rolls into two variables the same way.
