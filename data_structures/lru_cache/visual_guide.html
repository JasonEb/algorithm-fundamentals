Hash + Recency Order · O(1) get and put

LRU Cache

A fixed-size cache that remembers only what's been used recently — every real caching layer you've ever touched (browser cache, CDN edge cache, a Redis eviction policy) uses some version of this exact idea.

  • Fixed capacity. Set once, at construction — never changes.
  • get(key) returns the value if present, else -1 — and counts as "using" that key.
  • put(key, value) inserts or updates — also counts as "using" that key.
  • Over capacity → evict the least recently used key, not the oldest-inserted one. Those aren't the same thing once a key gets reused.
  • Both operations must be O(1) average time — not O(log n), not O(n). That's the whole design constraint.

The trap

Why a plain hash isn't enough — except in Ruby

A hash alone gives you O(1) lookup, but it doesn't remember order of use — so finding "the least recently used key" means scanning everything, O(n). That's why the textbook answer in most languages is a hash plus a doubly-linked list: the hash gives O(1) lookup, the linked list gives O(1) "move this to the front" and O(1) "evict from the back," and every node lives in both structures at once.

Ruby sidesteps needing the second structure entirely: Ruby's Hash preserves insertion order, and re-inserting an existing key moves it to the end without changing anywhere else. Delete a key, then set it again, and it jumps to the "most recent" end for free.

Hash + linear scan for LRU

O(1) get · O(n) put

Ruby Hash, delete + re-insert

O(1) get · O(1) put

No linked list needed — order is already tracked for you.

Mnemonic: "Touch it, move it to the back." Every get or put on an existing key deletes and re-inserts it — nothing else changes. The front of the hash is always the least recently used; the back is always the most recent.

If Ruby's Hash didn't do this for you

The classic hash + doubly-linked-list approach

This is what most languages need, and it's a fair follow-up question even in Ruby — "what if you couldn't rely on insertion order?" A doubly-linked list tracks recency directly: one end is most-recently-used, the other is least. The hash maps each key to a direct reference to its node in that list, not to the value — that's what makes O(1) both ways possible.

Once you hold a direct pointer to a node, splicing it out of wherever it sits takes O(1) — but only because the list is doubly linked. Removing a node means reconnecting its neighbors to each other (prev.next = node.next and next.prev = node.prev), and that needs the node's prev pointer directly. A singly-linked list only gives you next — finding what points *to* a node would mean scanning from the head, which is exactly the O(n) cost this whole structure exists to avoid.

Ruby — same interface, no reliance on Hash ordering
class Node
attr_accessor :key, :value, :prev, :next
def initialize(key = nil, value = nil)
@key = key
@value = value
end
end
class LRUCache
def initialize(capacity)
@capacity = capacity
@map = {}
@head = Node.new # sentinel: most-recently-used side
@tail = Node.new # sentinel: least-recently-used side
@head.next = @tail
@tail.prev = @head
end
def get(key)
return -1 unless @map.key?(key)
node = @map[key]
remove(node)
insert_at_front(node)
node.value
end
def put(key, value)
if @map.key?(key)
node = @map[key]
node.value = value
remove(node)
insert_at_front(node)
else
node = Node.new(key, value)
@map[key] = node
insert_at_front(node)
if @map.size > @capacity
lru = @tail.prev
remove(lru)
@map.delete(lru.key)
end
end
nil
end
private
def remove(node)
node.prev.next = node.next
node.next.prev = node.prev
end
def insert_at_front(node)
node.next = @head.next
node.prev = @head
@head.next.prev = node
@head.next = node
end
end

@head.next is always the most-recently-used entry; @tail.prev is always the one to evict. I verified this exact implementation against the official example, the capacity-1 case, and the update-refreshes-recency case — all three pass identically to the ordered-Hash version above. The sentinel @head/@tail nodes are what let insert_at_front and remove stay branch-free: there's no "is the list empty" special case, because the sentinels always give every real node something to link against.

Naming the behavior, not just the pointers

Refactor: methods that describe what get and put are doing

The version above works, but remove(node) followed by insert_at_front(node) shows up twice — once in get, once in put's update branch — with no name for what that pair of calls actually means: this node was just used. Pulling it into its own method turns two lines of pointer-splicing into one line that says what happened.

Ruby — same behavior, three named steps
def get(key)
return -1 unless @map.key?(key)
node = @map[key]
move_to_front(node)
node.value
end
def put(key, value)
if @map.key?(key)
node = @map[key]
node.value = value
move_to_front(node)
else
insert_new(key, value)
evict_if_over_capacity
end
nil
end
private
def move_to_front(node)
remove(node)
insert_at_front(node)
end
def insert_new(key, value)
node = Node.new(key, value)
@map[key] = node
insert_at_front(node)
end
def evict_if_over_capacity
return unless @map.size > @capacity
lru = @tail.prev
remove(lru)
@map.delete(lru.key)
end
# remove(node) and insert_at_front(node) are unchanged from above.

Read get and put out loud now: "find it, mark it used, return its value" — and "if it exists, update it and mark it used; otherwise insert it and evict if that pushed us over capacity." The pointer mechanics haven't changed at all — remove and insert_at_front are byte-for-byte what they were — they've just been pushed down a level so they stop competing with the public method's own logic for your attention. Verified against all three call sequences above; identical results before and after the refactor.

Bugs worth knowing before they bite you

Common mistakes

  • Ruby's implicit return leaks internal values out of put.

    If the last line executed in put is @cache.delete(oldest_key) (which happens exactly when an eviction fires), the method returns the evicted value instead of nil — because Ruby methods return whatever their last expression evaluated to. I caught this by actually running the code: put was returning 2 instead of nil on the exact call where eviction happened. Fix: put an explicit nil as the last line of the method.

  • @cache.keys.first is O(n), not O(1).

    .keys builds a brand-new array of every key before you ever call .first on it — silently turning your O(1) eviction into O(n). Use @cache.first directly, which returns the first [key, value] pair without materializing the rest.

  • Forgetting that put on an existing key must also refresh recency.

    Updating a key's value counts as "using" it, same as get does. If put only overwrites the value without deleting-and-reinserting the key first, that key keeps its old position — and can get evicted even though it was just touched.

Recap

Complexity, and where this goes next

Time

O(1)

get and put are each a constant number of hash operations.

Space

O(capacity)

The cache never holds more than capacity entries at once.

Likely follow-ups if this comes up in an interview: "What if this needed to be thread-safe?" (a mutex around get/put, or a concurrent-safe structure). "What if entries needed to expire after a fixed time, not just by capacity?" (store a timestamp alongside each value, check it in get). "What about LFU instead of LRU?" (evict by frequency of use instead of recency — genuinely harder, needs a frequency-bucketed structure). "How would you do this in a language without an ordered hash?" — that's exactly where the hash + doubly-linked-list textbook answer comes back in.
