Recursion · dynamic programming

Top-down vs bottom-up

Two ways to build the same answer from smaller subproblems — one starts at the full problem and recurses down, the other starts at the base case and loops up. The right choice depends on the shape of the subproblems, not personal taste.

top-down (recursive) bottom-up (iterative) where it costs you

Same answer, opposite shape

Top-down makes the full-size call first and has to wait on the stack; bottom-up never calls the full-size problem at all — it just loops until it gets there.

The same function, both ways

Using lcm as the running example — identical math, opposite control flow.

Top-down
def lcm(n)
  return 1 if n == 1

  smaller = lcm(n - 1)
  candidate = smaller
  while candidate % n != 0
    candidate += smaller
  end
  candidate
end
Bottom-up
def lcm(n)
  result = 1
  (2..n).each do |i|
    candidate = result
    while candidate % i != 0
      candidate += result
    end
    result = candidate
  end
  result
end

When bottom-up wins: every subproblem is needed anyway

lcm(6) genuinely needs lcm(1) through lcm(5) — there's no way to skip any of them. When the dependency chain is a straight line like this, bottom-up computes exactly what top-down would, minus the recursive call overhead and minus any stack-depth risk.

When top-down wins: only some subproblems are needed

Computing baseexp by halving the exponent instead of subtracting 1: power(2, 8) only ever touches 8 → 4 → 2 → 1 → 0. A bottom-up table built from 0 up to 8 would compute five values (3, 5, 6, 7, and whatever else) that this call never needed.

Top-down (fits naturally)
def power(base, exp)
  return 1 if exp == 0

  half = power(base, exp / 2)
  square = half * half
  exp.odd? ? square * base : square
end
Bottom-up (wasted work)
def power(base, exp)
  table = [1]
  (1..exp).each do |i|
    table[i] = table[i - 1] * base
  end
  table[exp]
end
# computes every exponent 0..exp,
# even ones power(2, 8) never asked for

When top-down needs help: overlapping subproblems

Naive Fibonacci (no memo) recurses on two smaller inputs, and those subtrees overlap. Computing fib(4) this way makes 9 calls total — but only 5 distinct values (0, 1, 2, 3, 4) are ever actually needed.

Top-down + memo
def fib(n, memo = {})
  return n if n <= 1
  return memo[n] if memo.key?(n)

  memo[n] = fib(n - 1, memo) +
            fib(n - 2, memo)
end
Bottom-up
def fib(n)
  return n if n <= 1
  table = [0, 1]
  (2..n).each do |i|
    table[i] = table[i-1] + table[i-2]
  end
  table[n]
end

Stack depth is a real cost, not a theoretical one

Earlier in this exercise, a version of lcm that recursed by walking downward from n! to 1 hit an actual SystemStackError at n = 8 — 40,320 nested calls was already too deep for Ruby's default stack. Bottom-up has no equivalent failure mode: a loop doesn't add a stack frame per iteration, so depth is never a constraint.
